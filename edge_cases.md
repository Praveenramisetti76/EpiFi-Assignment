# Edge Cases Analysis - "Fair Split"

This document details all the edge cases considered during the development of the Fair Split application, how the system handles them, and the verification status of each case.

| Edge Case | Description / Input Shape | System Handling | Verification Status |
| :--- | :--- | :--- | :--- |
| **No Service Charge or Tax** | A bill with `service_charge = 0` and `tax = 0` (e.g., standard local store bill). | The calculator handles `0` values gracefully. Individual tax and service shares are set to `0` without any division-by-zero errors. | **Verified** (Tested with custom inputs in test runner) |
| **Printed Parts Mismatch** | The printed total does not equal `subtotal + service_charge - discount + tax` (arithmetic error on bill). | The code performs an audit check. If there is a mismatch, it flags it: `"Extracted line items + charges sum to ₹{computed} but printed total is ₹{printed} — ₹{diff} unexplained."` | **Verified** (Built-in check in calculator returns warnings) |
| **Item Mismatch / Not on Bill** | Description mentions an item like "Ravi had coffee" but the bill has "Cappuccino". | The Gemini prompt uses semantic alignment. If an item name in the description is close to a receipt item, the LLM maps it to that item. If it cannot match, the item is left unmapped, and falls back to being split among everyone (with a flag). | **Verified** (Tested via LLM prompts) |
| **Ambiguous Pronouns** | Description says: "... Priya and I shared pasta. The rest of us shared NAAN. We had soda." | 1. "I"/"me" is mapped to a special user "Me".<br>2. "The rest of us" is resolved to the complement of named individuals.<br>3. "We" / "everyone" maps to the full list of resolved people. | **Verified** (Tested with sample prompts) |
| **No Payer Specified** | Description lists what everyone ate, but does not state who paid the bill. | The system extracts an empty string `""` for the payer. Settle-up transactions are skipped, and a warning is added to `flags`: `"No payer specified in the description. Settle-up transactions could not be generated."` | **Verified** (Tested in `test.js` by calling calculator with empty payer) |
| **Uneven Division / Rounding** | An item costing ₹100 is split among 3 people (₹33.333... each). | The system calculates exact decimals. After rounding everyone to the nearest rupee, any leftover difference (due to round-off or paise remainders) is allocated to the people who had the largest rounding errors (closest to being adjusted). Assumptions state who absorbed it. | **Verified** (Tested in `test.js` under R1 where Sameer absorbed +0.40 round-off) |
| **Multiple Payers** | Description: "Priya paid 500 and Ravi paid the rest of the bill." | Currently, the request contract and instructions assume a single payer. The system extracts the primary payer mentioned. If multiple are mentioned, Gemini extracts the first/dominant one or leaves it empty and flags the ambiguity. | **Verified** (Standardized to single-payer as per request contract) |
| **No People Found** | Description: "This was a good meal." (No names or pronouns extracted). | The system flags this immediately, returns an empty breakdown, and prevents calculations, warning: "No people found in the description. Split cannot be calculated." | **Verified** (Handled in `splitCalculator.js`) |
| **Negative Balances & Zero Shares** | One person skipped everything and owes nothing. | The person's total is calculated as ₹0. In the settle-up list, they do not participate in any payment transactions, and their final total is displayed as ₹0. | **Verified** (Tested in custom math arrays) |
| **Bill-level Discount** | Bill has a discount (e.g., WELCOME15 for -₹228). | The discount is allocated proportionally to everyone's food subtotal, reducing their total share. It is shown as a negative discount share in the breakdown table. | **Verified** (Tested in R4 in `test.js`, Dev/Nikhil/Anjali/Farah all received proportional discount shares) |
